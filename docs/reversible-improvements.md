# 老板试用阶段：逐项改进与撤回方案

状态：仅检查和提案，尚未批准或实施功能改动。

## 工作方式

每次先说明一项改进的效果、涉及范围、关闭或撤回方式及影响。用户确认该项后才实施，完成后提供验证结果，等待用户确认效果，再开始下一项。不捆绑无关重构，不增加不必要的必填项。暂不 commit、push 或部署。

界面调整一般通过独立的小范围代码差异撤回，无需开关。数据库、权限、业务状态变更必须先说明影响；代码撤回不能自动撤销已经产生的业务资料。

## 根据现有代码提出的候选项目

| 候选项目 | 建议方式 | 关闭或撤回后的行为 | 影响与优先级 |
| --- | --- | --- | --- |
| 单据常用签名 | 可选：单独控制常用签名的载入和保存入口 | 仍可每张单据手写、确认并保存签名 PDF；保留常用签名和历史 PDF，恢复开启后可继续使用 | 建议作为第一项开关试点。主要涉及 `DocumentSigning.tsx`、常用签名 API；不需要修改签名表结构 |
| 工作照片新增上传 | 可选：仅控制新增上传 | 工作单、安排与状态更新继续使用；已有照片仍按原权限查看 | 已有独立 `JobPhotos` 组件及照片 API。关闭不删除 Storage 文件，不修改员工工作单访问规则 |
| 费用收据新增上传 | 可选：仅控制新增上传 | 费用录入和现有审核流程继续使用；已有收据仍可按原权限查看 | 已有独立 `ExpenseReceipts` 组件及收据 API。不把附件改成必填，不改变审核条件 |
| 新增单据签名 PDF | 可选，但后于常用签名试点 | 普通未签名打印继续使用；历史签名 PDF 仍可下载 | 当前普通打印与签名版独立。只关闭新增签名，不隐藏历史记录，不撤销原有签名 |
| 总览文字、按钮与信息布局 | 按老板反馈逐项调整，通常不设开关 | 撤回该项布局或文字差异即可 | 当前总览已有待处理入口和今日工作；避免再增加重复入口和额外填写步骤。具体布局待反馈后提出 |

以上是可选方案，不建议现在全部实施。现有组件独立有利于限制修改范围，但仍须检查所有调用位置、API 和关联流程。

## 不建议作为普通开关的功能

- 用户权限、员工工作单可见范围、操作日志：保留授权和审计能力，不能用功能开关代替角色与资料归属检查。
- 报价转发票／工作单：现有数据库 RPC 会建立真实记录及关联，关闭入口不等于撤销已经转换的业务资料。若要改流程，先说明关联、重复转换限制和回退处理。
- 发票状态、费用审核、工作安排与状态：属于现有业务流程，须单独提出影响方案，不作为本轮随手关闭的附加功能。
- 数据库表、Storage bucket、既有迁移：不通过删除表或文件实现功能关闭；本次没有检查线上迁移应用状态或真实资料。

## 开关实现建议（待确认）

先按选中的一项实现，不先建设整套设置系统。对于全系统的可选操作，建议后端统一配置并向已登录前端提供对应的功能状态；前端据此显示入口，后端在原有身份、角色、资料归属检查基础上检查是否允许该操作。授权仍由原有机制负责，开关开启不能扩大权限。关闭写入时保留历史读取 API 的原有授权。

第一阶段可由开发者根据老板选择修改服务端配置；不使用浏览器本地开关控制全系统行为。如果老板需要自行即时切换，再另行确认仅老板可修改的设置页、持久化设置及操作日志方案，这可能涉及数据库迁移，应在实施前单独说明。配置方案是否需要重启取决于最终实现，实施前说明生效方式。

现有功能默认保持当前开启行为；新增功能的默认值在该项方案中明确。关闭不强制刷新或丢弃正在填写的表单；提交时若操作已关闭，应保留输入并明确提示。已经完成的上传或签名继续保留；进行中的请求如何处理，应在该项实施前确定。

## 每项交付的检查标准

1. 说明并演示开启后的效果与关闭后的原有使用路径，不增加多余输入。
2. 检查老板、管理员、员工的相关权限；直接调用 API 也不能绕过限制。
3. 检查关闭、重新开启及历史资料读取；不删除或修改真实资料来验证。
4. 提供该项涉及的文件、验证结果、代码撤回方式，以及已经产生的资料为何不会随代码撤回。
5. 等用户确认效果，再处理下一项。仅文档变更无需运行应用测试；功能实施时按相关行为进行验证。
