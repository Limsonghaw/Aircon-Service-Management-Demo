# 从旧 PDF 带入项目：实施及验收

## 范围与流程

仅扩展现有新增报价／发票表单，保留手动新增、项目增删、总计及原有 PDF 模板。历史归档①及其统计排除规则不变。

1. 选择参考 PDF，在浏览器本地使用已安装的 pdfjs-dist 读取文字与坐标，不新增依赖，不调用外部 OCR／AI。
2. 按文字行、项目编号及明确的表格列形成候选项目。说明、数量和单价均可在核对区修改。缺失／冲突的数值不猜填。
3. 核对后明确点击加入。已有项目保留；报价仅移除完全未填写的初始空行。若发票已有手填总金额，先确认改用项目计算。重新识别覆盖核对区前也须确认。
4. 客户、编号及日期由用户填写确认。原文件可查看，旧编号／日期／付款状态不带入。最多 10 MB、10 页；超过页数拒绝识别，避免悄悄忽略后页。扫描及手写不做 OCR，提示手动核对。
5. 用户点击保存后先调用原有单据保存，再上传独立参考附件。参考上传失败时保留文件及已确认的单据 ID、锁定表单，重试只上传附件，不重复建立单据。
6. 保存后的参考原件在单据编辑面板的「参考原件」中查看／下载。与历史归档、老板签名及客户签回文件分开。

文件仅在当前页面内存保留。识别／上传期间有离开保护；未保存时离开会警告。若强制关闭浏览器或确认放弃，需从本机重新选择文件。单据已保存但附件失败的提示会明确说明，不能把关闭页面理解为撤销新单。

参考原件不影响账目或付款状态；用户确认保存的新发票按现有发票业务规则进入统计。识别不自动认定已付款。

## 测试环境与限制

所有接口写入测试均为独立 QA 数据：前端使用临时本机静态站点和完整 API 拦截；后端使用测试主机及模拟 Storage／数据库 HTTP。没有调用真实 Supabase 写入、修改账号权限、执行迁移、部署或重启业务服务。

- 前端 Node 测试：97 项通过，包括多行说明、多个项目、现有表格列、缺失数值、冲突金额及①的列表逻辑。
- 后端：254 项通过，包括新增参考接口的老板／管理员访问、员工／匿名／失效身份拒绝、跨单据／跨类型访问拒绝、文件校验、失败重试、不可覆盖及内容完整性。
- 前端 build、lint 通过；构建仍提示现有较大 bundle。后端编译通过，但网络限制导致 NuGet 漏洞数据库检查不可用，不等同于已完成依赖安全扫描。
- 浏览器：1440×1100、390×844，报价及发票导入／核对／编辑／保留已有项目／保存／附件失败重试／保存后清理离开保护。实际截图与结果在 `output/reference-import-qa/`。
- 识别失败浏览器场景：损坏 PDF 保留所选文件并可重试、扫描图片不生成猜测项目、识别中阻止取消离开、关闭页面触发未保存警告，整个识别过程零业务写入。
- 用户提供的报价样本仅在本地读取，识别两项；第一项明确 one unit、8850，第二项 1100 仅为参考金额，数量与单价留空；未上传样本，未保存真实单据。
- 无真实旧发票样本：已用独立 QA 表格测试数量／单价列，不能据此保证任意旧发票版式。现有生成发票模板未修改。

真实数据库迁移、真实 Storage 保存／读取、真实登录与端到端业务流程均尚未验证，须先批准迁移；部署或重启仍须另行授权。

复现浏览器 QA：在 frontend 目录设置 `NODE_PATH` 为已安装的 Playwright/pdf-lib 模块目录后运行 `node tests/referenceImport.qa.cjs`。可选环境变量 `QA_SAMPLE_PDF` 指定本机报价样本，只测试提取，不上传。浏览器脚本不会连接真实 API。
