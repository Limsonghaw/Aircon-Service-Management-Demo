# Job 工作照片

## 数据库与配置

- 在已完成 202610010006 的数据库执行 `supabase/migrations/202610010007_add_job_photos.sql`，成功后不要重复运行。
- 使用现有后端 Supabase URL 和 service-role key；没有新增依赖或前端密钥。
- 新建私有 `job-photos` bucket 和 `job_photos` 表；浏览器不直接访问 Storage，也不会得到 service-role key、Storage 路径或公开链接。
- 反向代理必须允许至少 11 MB 单次请求。多选照片按顺序单张上传，不是一份巨大 multipart 请求。
- 备份需要同时包含 `job_photos` 表和 `job-photos` Storage 文件。只备份 PostgreSQL 不包含照片内容。

## 使用

1. 在工作单（员工为「我的工作」）点击「工作照片」。
2. 手机可点击「拍照」调用系统后置相机，也可点击「从相册选择（多选）」一次选择多张。电脑使用文件选择器；拍照按钮只在手机宽度显示。
3. 可以继续拍照/选择，把照片加入待上传列表，或移除尚未上传的单张照片。
4. 点击「上传照片」，逐张保存并显示进度。保存后显示缩略图，可打开原图及下载；关闭后重新打开仍可查看。

格式为 JPG/JPEG、PNG，每张最多 10 MB。PDF、SVG、HEIC/HEIF 不接受，也不会自动转换。iPhone 若传回 HEIC，请先导出为 JPG；不能承诺所有浏览器均自动转换。相册按钮没有 capture 属性，相机 input 有 `capture="environment"`；实际相机/选择器行为由手机系统和浏览器决定。

不自动改变工作状态，不设计工作完成确认单，不加入签名。照片按原始文件保存，可能含 EXIF 拍摄信息，不会自动移除或修改。

## 权限与完整性

- 老板、管理员可查看/上传所有存在工作的照片。
- 员工必须绑定有效 employee，该 employee 的团队及成员都启用，并且团队名称匹配工作当前的团队。
- 列表、上传、原图和下载每次均查询当前数据库权限，不仅依赖登录 cookie。改派、解绑或停用后，后续请求被禁止。
- 上传登记 RPC 在事务中锁定用户、工作及员工/团队资料，重新检查权限，原子写入照片元数据和 `job_photo_uploaded` 操作日志。
- 文件名称/格式/大小由服务器验证；下载检查预期路径、长度和 SHA-256。格式验证复用现有收据校验，不是杀毒扫描或完整图片解码。
- 照片外键阻止删除仍有照片的工作，避免证据丢失。页面不提供照片删除；管理员需要维护时应先完整备份，再按精确 ID 处理元数据及 Storage 文件，不得批量清空 bucket。

## 失败处理

- 每张成功照片立即进入已保存列表，从待上传列表移除。任何失败均停止该批次，未尝试的照片保留。
- 明确的数据库拒绝会清理本次尚未登记的上传文件。未知结果或超时不删除可能已登记的文件；先刷新检查，避免重复。
- 前端遇到不确定结果会移除当前不确定项目并暂停上传，必须刷新列表检查后才允许继续。用户确认未保存后再重新选入该张照片。
- 离开页面后不继续发起下一张上传；正在执行的单张可能已经保存，返回后重新查询列表。
- 管理员排查孤立文件时必须比对 `job_photos.storage_path`、创建时间与后端日志，不可仅凭一次超时删除文件。
